# Privacy and data handling

PostgreSQL stores existing registration/contact and membership/session metadata plus issuer configuration, public metadata/images, immutable versions, assignment scopes, pseudonymous issuance state, safe lifecycle events, status references and reissuance blocks. Configuration claim **definitions** are stored; returned participant claim **values** are not.

Each request records tenant/configuration/dependency versions, HMAC subject and idempotency references, step/state/expiry, safe codes and trusted public status/opaque handle. Events allow only tenant/configuration/request/subject-hash/type/actor-hash/time. The schema has no arbitrary history payload column. Survey answers, participant JWTs, proof material, preauthorization data, offer URLs, raw claims and complete credentials remain transient and are not saved in ORCE/global context or SQL. The browser displays an ephemeral offer/QR; it does not store it in local/session storage.

Pools, mail transports, locks and token/native state use a process-owned module cache, independent of Node-RED's configured context storage. Upgrade clears the previous `fapPciPgPoolHolder` and `fapPciMailerHolder` context keys. If earlier versions used disk-backed context, inspect its historical snapshots/backups for connection details and apply the approved retention/remediation process. A cleanup warning requires operator investigation.

Subject HMACs use the existing verification pepper with a tenant prefix. Treat this pepper as long-lived: rotating it without a migration breaks pseudonymous lookup and reissuance blocks. It must remain in the runtime Secret, not source or reports. Keycloak subject IDs in administrative membership/assignment tables and the tenant-scoped history association are administrative personal data, separate from retrieved credential claims. An authorized issuer can search current IAM username, email and name; the response generates a short-lived history-only JWT with a separate type, audience and derived MAC key. This JWT is not an IdP token and is never persisted. A verified public holder key is recorded as did:jwk for audit. These controls do not themselves constitute GDPR certification.

Unexpected errors and mail/reconciliation failures use safe codes; raw error messages, upstream payloads and request objects are not emitted to Node-RED logs. Unexpected failures include bounded source stack frames and a correlation ID for diagnosis. Periodic internal results do not broadcast tenant lists through uibuilder. No debug nodes are added. Source tests assert the transient credentials/claims never enter the test store. Ephemeral test keys/certificates are generated in memory, including the local mTLS handshake; no material is archived.

Full live evidence must inspect PostgreSQL, ORCE context backends, NATS streams, proxy/body logs, telemetry, crash captures, browser storage and backups after both successful and failed issuance. Confirm the exact approved OCM subjects use non-durable request/reply for sensitive payloads. PCI adapters and the reference gRPC service exclude bodies, headers and returned credentials from logs. The release includes reviewed-revision payload-log patches for the selected upstream issuer/signer/verifier; their deployed remediation is still unverified; the source locations and required canary scans are recorded in [operating profiles](../known-gaps.md).

Pending requests expire after ten minutes; maintenance records expiry once. Issued/revoked histories and immutable versions are retained. Public verification dependencies remain available while their tenant is active, including after configuration archive. There is deliberately no guessed automatic purge schedule: agree retention, pseudonym rotation, deletion/legal holds and credential-validity dependencies before implementing a cleanup policy. A deleted tenant keeps a tombstone, administrative/audit data and immutable history pending the approved data-retention policy. Its public UI/DID/JWKS/status/issuer routes, owned configuration and account/Secret grants are removed per FR-27/66. Shared OCM workloads and an independent participant repository are outside that deletion target.

Manual journey claims use a private service-closure map on the process-owned ORCE runtime, with no context-storage or SQL fallback. It holds only mapped claim values and completed mapped-step markers, bound to tenant/request/subject hash and every pinned dependency version. Limits are 1,000 pending forms and 16 MiB of encoded entries including a fixed per-entry allowance; admission fails rather than evicting another user's answers. Maintenance and cache access remove expired entries. Consumption removes the cache entry before participant/signing work; completion clears transient references on both success and failure. Offer failure, tenant lifecycle changes and denied owner authorization discard the corresponding values. Runtime replacement and Function-node shutdown clear the map explicitly. Unmatched survey answers are never placed in the map. A browser refresh retains only the request identifier; runtime loss requires form re-entry before an offer or a fresh request after one. These values are self-declared claims, not evidence that a participant verified the entered name.

Persistent connector circuits store only tenant/connector identifiers, failure count, open-until time and an optional recovery request ID. Defaults are three dependency failures and a 30-second pause; configuration bounds are 2–10 failures and 1–300 seconds. Database tenant locks permit one recovery probe, with a timeout lease. Authorization failures do not count as connector outages. Actual SQL contention and deployed transport behavior remain LIVE REQUIRED.
