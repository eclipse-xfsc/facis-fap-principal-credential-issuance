# 0.5.0-rc.12

The neutral source revision preserves this signer fix and replaces operator-specific examples. See [revision changes and validation](neutral-revision.md) and [neutral configuration](../operations/neutral-configuration.md). Historical deployment observations below do not certify this revised package.

This release fixes the native signer-key decoding failure observed at Alpha credential completion. It starts from the latest rc.11 source in the operator's allsources.zip, including the deployed discovery correction and temporary diagnostics. Earlier implementation and deployment history was checked against the previous conversation and the supplied deployment notes.

## Cause and correction

After the rc.11 public JWKS correction and issuance-service restart, discovery, token and nonce requests returned HTTP 200. The credential endpoint progressed from HTTP 401 to HTTP 400. Its native callback failed at credential-completion with PCI-SR2-VALIDATION: Algorithm/key mismatch. The diagnostic recorded ES256, keyType other and curve absent.

Crypto 2.3.7's JwkPublicKey method returns Crypto Core 2.3.0 GetJwk's array of JWKs. For EC P-256 this is a one-element array; RSA 2048 returns two entries with RS256 and PS256 algorithm metadata. The PCI private-key lookup accepted a bare JWK or a keys object, but returned this array unchanged. Spreading the array into the verifier produced numeric properties instead of kty/crv/x/y. The existing unit fixtures returned a bare JWK and missed the native wire contract.

backend/sr2/native.js now normalizes the native array, retained bare-JWK and JWKS representations, including JSON-encoded responses. It selects exactly one public key matching the configured key name or tenant DID and the credential's supported algorithm. It rejects malformed, ambiguous, foreign, private and incompatible key responses with PCI-SIGNER-JWK-INVALID. RSA algorithm variants are selected by algorithm, independent of array order. The verifier still checks the exact credential key ID, signature, lifetime, issuer, subject, claims, type, status and holder binding. No first-key fallback or verification bypass is introduced.

Temporary broad error-message and key-shape diagnostics are removed. Callback failure logs retain the error code and static stage. The live Alpha runner logs endpoint paths, HTTP status and allowlisted OAuth error codes. Offers, cookies, tokens, credentials and holder private keys are not written to the result log.

These are the source pins recorded for the supplied ESB baseline. The deployed container's exact build provenance was not independently verified here.

## Validation and deployment

Sixteen new cryptographic regressions run in ES modules and in the generated M11 Function-node VM without host clone globals. They reproduce the old array-to-key failure, verify JWT VC and both SD-JWT formats, exercise RS256/PS256 selection, retain older response forms, and reject tampering, holder mismatch and unsafe keys. See [validation.json](validation.json) for executed checks and limits.

The complete source and generated flow/UI/G0 artifacts are packaged. Follow the [rc.12 surgical upgrade](../operations/upgrade-0.5.0-rc.12.md). It uses the existing private rc.6 lifecycle configuration and changes PCI artifacts only. The previous issuance-service JWKS cache repair is already completed. Existing OCM deployments, keys, data, participant image and unsealed OpenBao require no changes for this source fix.

Live success remains to be verified on the operator's cluster with a newly created offer after upgrade. Local tests do not establish live issuance, PCM or full requirement acceptance.
