# 0.5.0-rc.16: resubmission of milestone 2

Release candidate for the resubmission of MS2. It is the first release candidate
built entirely through reviewed pull requests from the official repository, and the
first delivered as an application image built from the tagged source. Its acceptance
is decided by the principal's QA; this page records what changed since the submitted
baseline `2fa3a8af` (tag `qa-ready-22-10-2026`) and where the evidence for it is.

## Origin of the changes

The code of the maintainability work in this candidate was first prepared as a local
candidate (`rc.15`) with AI-assisted tools on 21 and 22 October 2026 and attached to
LEANEA's response of 26 October. That candidate was never pushed and is not part of the
history. Its content was split into the pull requests listed below, each limited to one
concern and passing every check on its own; the four behaviour fixes of the issuer
interface were separated from the refactoring and are preceded by their failing tests.
The vendored copy of `acorn`, the split SQL strings and the release and provenance
records of that candidate were not carried over. Every commit that carries part of it
says so, and the files prepared with AI-assisted tools carry the disclosure in their
header (`tools/licence-header-ai-files.txt`).

## Changes

Repository and pipeline (R1): Eclipse Dash licence check green through a constraints
pin of `markdown` (IP Team request filed in parallel), CI runners pinned to
`ubuntu-24.04`, pull-request template with size, author, AI disclosure and named
reviewer; dependency and vulnerability scans for Node.js, Python and Go, secret scan,
manifest schema check; dependency updates reported as issues instead of pushed.

Maintainability of the source (R2, R3): `acorn` taken from the npm registry and the
module syntax stripped by syntax instead of by regular expression; an AST-preserving
source formatter applied once to `backend`, `src`, `shared`, `tools` and `test`; the
backend split into adapter contracts, native keys, native metadata and service policy
with 24 hardening tests; bundle-graph checks and a maintainability gate with committed
rules, extended to `backend/` with a documented exception list; the issuer interface
split into state, eleven action modules and nine view modules without behaviour change,
followed by five fixes each with its failing test first (busy flag across overlapping
operations, connector draft aliasing, wallet return navigation, privileged state on
refresh, hashchange listener removal); the SR2 transport wrapper, the native adapter
factory and the authentication node refactored into small functions after
characterisation tests; copyright and licence headers with SPDX identifiers on every
authored source file.

Tenant theme (R2-10, FR-PCI-60): each tenant chooses its accent, page and text colors
within the contrast rules, one of five bundled font stacks, the corner style and the
page width; the theme applies as soon as the branding is activated, and the provider
and registration pages keep the FACIS standard.

Testing (R2-7): the deployed UX test runner for FR-PCI-61 with the twelve `@pci-ux`
scenarios, the environment collector and the run summary; DOM fixture regression in
CI; the formatter and the line rules of the gate cover `test/`.

Documentation (R2-8, R3-7): requirements catalogue with the historic labels retained
and no row shown as current acceptance; the gap register of the two October status
matrices; the acceptance gates; NOTICE completed; the fork-based contribution and
review workflow; the maintainer guide with the request-flow chapter; every page in the
navigation; the M17 tenant identity tab described; the site published from `main` and
from every release candidate tag, with a troubleshooting and FAQ page (R3-8).

Build and deployment (R4): the application image on `ecofacis/xfsc-orce:2.0.15` by
digest with first-start seeding of `/data`, the participant image, the `Images`
workflow (build, scan against the base image, SBOM, start-up check, publication
through the `eclipse-xfsc/dev-ops` workflows), the backup and rollback procedure and
the deployment guide for the image; the collection of the captures for the privacy
canary scan and a deployment record that binds a running installation to its tag,
commit and image digests (R4-3); the deployment repository package generated from the
source by `tools/export-deployment-package.mjs`, ground-zero and the charts stating the
release version, checked by a test (R4-4).

Release (R6): version `0.5.0-rc.16` in `VERSION`, the package files, the three charts,
the API documents, the integration lock and the release workflows; the
[requirement-to-test matrix](requirement-test-matrix.md) with the 23 requirements
under reassessment; the [table of quality assurance commitments](qa-commitments.md);
the [pull-request record](pull-requests.json); the release inventory.

R2-10, R3-8, R4-3 and R4-4 were added after the remediation plan of 30 October; they
close gaps that would otherwise be submitted as deviations.

## What this candidate does not claim

No pull request of this candidate has been reviewed or merged at the time this page is
written; the pull-request record states for each one what has taken place. No image
built by the workflow has run on IONOS or OSC; the deployed BDD Executor run, the
end-to-end, Helm lifecycle and security tests and the demonstration are work package
R5 and are recorded with the digests they ran against. The deployment repository
receives the package of this candidate through its own pull request, merged by its
maintainers. The CI results of earlier
commits in [executed checks](completion.md) belong to those commits. The gates that
remain open are listed in [acceptance gates](acceptance-gates.md).

## Upgrade

Installations deployed from the image: change the image of the ORCE container to the
digest of this candidate after the backup of
[backup and rollback](../operations/backup-rollback.md); the first start seeds `/data`
(see [deploying the application image](../operations/deployment.md#deploying-the-application-image)).
Installations maintained with the hot installer: `automation/stage1/install.sh` with
the `dist/` of this candidate, as for earlier release candidates.
